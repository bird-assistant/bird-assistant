# 视觉线结论：摄像头里能不能快速发现鸟并给出候选物种

> 数据截止：2026-10-22。全部 CPU 推理，代码与命令见 [README](识别技术预研-README.md)，原始汇总见 [results/summary.md](../results/summary.md)。

## 1. 一句话结论

**"发现鸟"可以在普通笔记本 CPU 上实时做到**（720p 源、yolo11n@640、端到端 p50 24 ms ≈ 41 FPS，等价于 29.97fps 源的 1.07 倍实时），
但**只对画面里 ≥64px 的鸟可靠**（召回 0.88–0.94）；**"给候选物种"目前不可用**——现成 ImageNet 分类器词表不覆盖目标鸟种，top-1 在同一只鸟上逐帧抖动（每 track 平均 3.1 个不同标签）。

## 2. 实验设置

| 项 | 值 |
|---|---|
| 设备 | Intel Core Ultra 9 275HX（24 线程）/ 63.4 GB / Windows 11，**无 GPU 参与** |
| 软件 | Python 3.13.9, torch 2.14.1+cpu, ultralytics 8.4.183, OpenCV 5.0.0 |
| 检测 | yolo11n（COCO `bird`=14），`conf=0.25`, `iou=0.5` |
| 跟踪 | ByteTrack（`bytetrack.yaml`，`persist=True`） |
| 物种 | torchvision ResNet50 / EfficientNet-B0（ImageNet 权重，仅保留 59 个鸟类类别） |
| 输入 | V1: 1280×720 @29.97fps，取前 300 帧（10 s）；V2: 720×576 @25fps，前 300 帧 |
| 参照（pseudo-GT） | yolo11x@1280，300 帧 |

**关于参照**：第 1 周没有人工标注。所有"召回"都是"相对 yolo11x@1280 的参照召回"（IoU≥0.5 或 0.3 匹配），用于横向比较分辨率/退化条件，**不是绝对精度**。抽样人工核对过 3 帧（见 `results/frames/`），框质量可接受。

## 3. 速度（300 帧均值，CPU）

| 配置 | 检测 p50 | 分类 p50 | 端到端 p50 | p95 | 处理帧率 | 实时比* |
|---|---|---|---|---|---|---|
| n@640 检测+跟踪 | 17.6 ms | — | **24.2 ms** | 27.0 ms | 32.2 FPS | **1.07×** |
| n@640 + EfficientNet-B0 | 17.5 ms | 11.6 ms | 35.6 ms | 39.8 ms | 30.3 FPS | 1.01× |
| n@640 + ResNet50 | 18.0 ms | 26.8 ms | 51.1 ms | 56.9 ms | 22.9 FPS | 0.76× |
| n@1280 检测+跟踪 | 44.2 ms | — | 52.9 ms | 57.8 ms | 16.6 FPS | 0.55× |
| x@1280（参照） | 832 ms | — | 841 ms | 906 ms | 1.2 FPS | 0.04× |

\* 实时比 = 处理帧率 ÷ 源帧率(29.97)，1.0 表示刚好实时。

要点：

- **检测本身很便宜**（17.6 ms），第二段物种分类才是主要开销；ResNet50 直接把 p95 从 27 ms 推到 57 ms，EfficientNet-B0 只需 11.6 ms。- 分辨率从 640 提到 1280，耗时约 2.5 倍、召回只涨 5.5 个百分点（0.646→0.701），**实时档不该用 1280**。
- yolo11x 在 CPU 上完全不可用（1.2 FPS），只能当离线参照/云端方案。
- 全部数字含"读帧 + 推理 + 跟踪 + 画框 + 写视频"，不是纯推理时间，所以偏保守。

## 4. 检测质量（参照召回）

| 条件 | 总召回 IoU0.5 | 总召回 IoU0.3 | ≥128px | 64–128px | 32–64px | 误检率 |
|---|---|---|---|---|---|---|
| 干净 @640 | 0.646 | 0.673 | 0.880 | 0.132 | — | 4.1% |
| 干净 @1280 | 0.701 | 0.727 | 0.912 | 0.178 | — | 5.0% |
| 距离×2（整体缩到 0.5） | 0.587 | 0.633 | — | **0.901 / 0.942** | **0.055 / 0.110** | 7.3% |
| 低光（亮度×0.35+噪声） | 0.609 | 0.647 | 0.861 | 0.081 | — | 5.8% |
| 运动模糊（21px 线性核） | 0.523 | 0.568 | 0.876 | 0.058 | — | 9.6% |
| 遮挡（覆盖框 60% 面积） | 0.515 | 0.561 | 0.892 | 0.018 | — | 8.2% |

读法（**重要**）：干净场景的 64–128px 箱召回只有 0.13，不代表"64–128px 的鸟都检不到"。这一箱里主要是**背景里第二个鸟**（虚焦、被枝条挡住）。受控实验（整个画面缩到 0.5，鸟自然落入 64–128px）给出 **0.90**。所以真正的分界线是：

> **鸟的短边 ≳64px → 可用（≈0.9）；≲48px（32–64px 箱）→ 崩到 0.06–0.11。**

这也解释了为什么 @640 吃亏：1280 宽的源被缩到 640 输入，鸟的等效像素再砍一半，64px 的鸟在网络里只剩 32px。

## 5. 失败模式分类

| 失败类型 | 现象 | 证据 |
|---|---|---|
| **小目标** | 32–64px 召回 0.055；缩小后画面里 42 个预测几乎没有落在参照框上 | [fail_tiny_f150.jpg](../results/frames/fail_tiny_f150.jpg) |
| **遮挡** | 60% 面积的枝条遮挡后，≥128px 的召回仍 0.89，但被遮挡的次级小鸟完全丢失（0.018） | [fail_occluded_f227.jpg](../results/frames/fail_occluded_f227.jpg) |
| **运动模糊** | 飞行/晃动时召回掉到 0.52（降幅最大的一项），框容易只覆盖鸟身一部分 | 汇总表 `blur` 行 |
| **低光** | 召回 0.61，主要影响低对比度的小鸟；对主体大鸟影响不大（0.86） | 汇总表 `dark` 行 |
| **间歇漏检（易被忽略）** | 帧 16–22 连续 7 帧完全无框，鸟其实就在喂食器边缘（对照帧 15/23 都有框） | `results/V1/yolo11n_640_frames.csv` 中 frame 7–53 的缺口 |
| **定位偏差（非漏检）** | 帧 227 的苍头燕雀其实检到了（conf 0.50），但框偏大，IoU 0.44 卡在阈值下 | [fail_occluded_f227.jpg](../results/frames/fail_occluded_f227.jpg)（绿框 vs 红框） |
| **误检** | 4–10%，主要是枝条/果实；结论：可接受，靠面积+停留时间过滤 | 汇总表"误检率"列 |

成功样例（近距、顺光、无遮挡）：[success_bluetit_f030.jpg](../results/frames/success_bluetit_f030.jpg)（conf 0.87 / track #2）、[success_chaffinch_f250.jpg](../results/frames/success_chaffinch_f250.jpg)（conf 0.77 / track #42，连续 93 帧同一 ID）。

> "间歇漏检"这一条对产品设计影响最大：**不能把单帧检测当作"发现鸟"**，必须用"同一 track 连续 N 帧（N≈3–5）且框 ≥64px"来做确认，否则提示会一闪一闪。

## 6. 跟踪

V1 前 300 帧（10 s，实际约 2–3 只鸟）：

| 指标 | 值 |
|---|---|
| 唯一 track ID | 10 |
| ≥5 帧的 track | 5 |
| ≥30 帧的 track | 3 |
| 每一帧的框都带上了 ID | 100% |
| 最长 track | 93 帧（帧 206–299，同一只鸟停留） |
| 短 track（<5 帧） | 5（碎裂/掠过） |

结论：ByteTrack **够用**——停留的鸟能拿到稳定长 ID（93 帧不换号），但鸟飞出画面再回来、或被完全遮挡后会换号。
产品上不要用"ID 数"当只数，要用**"同一 ID 连续 ≥N 帧且框 ≥64px"作为"发现鸟"的触发条件**。

## 7. 物种候选：当前不可用，但原因很明确

ImageNet 59 类的实测输出（V1）：

| track | 帧数 | 聚合 top-5 | 真实物种 |
|---|---|---|---|
| 2 | 36 | goldfinch 0.54, brambling 0.17, jacamar 0.09 | 蓝山雀 |
| 34 | 40 | goldfinch 0.37, toucan 0.21, king penguin 0.14 | 苍头燕雀 |
| 42 | 93 | **brambling 0.95** | 苍头燕雀（燕雀科近缘，方向对） |

- 时序稳定性：相邻帧 top-1 一致率 0.81（ResNet50）/ 0.84（EfficientNet-B0），每 track 平均出现 **3.1–3.3 个不同标签**。
- 判读：模型学到的是"雀形目/燕雀科"级别的外观，但 **ImageNet 词表里根本没有蓝山雀（blue tit）**，最近邻只能是 goldfinch/brambling。
- 所以**不是"分类模型不行"，是"词表不行"**——这正好是下一步花钱最少、收益最大的一步。

## 8. 决策：直接用 / 微调 / 换方案

| 环节 | 结论 | 依据 |
|---|---|---|
| 检测（找鸟） | ✅ **直接用**（yolo11n@640 + ByteTrack） | 24 ms p50 / 27 ms p95、误检 <5%、≥64px 召回 0.88 |
| 跟踪 | ✅ **直接用**（ByteTrack） | ID 分配 100%，长 track 稳定 |
| 物种候选 | ⚠️ **换词表 + 轻量微调**（不是换架构） | ImageNet-59 无目标物种；同科近缘能排进 top-1，说明特征可用 |
| 小目标（<64px） | ❌ **方案层解决**：引导变焦/靠近，或"先录像再云端高分辨率切片分析" | 32–64px 召回 0.06–0.11，SAHI 也难补齐（网络输入只有 640） |
| 端侧部署 | ⏳ **未验证**（见 platform-constraints.md） | 本轮只在 PC 上验证可行性 |

## 9. 下一步（按性价比排序）

1. **D+1：换词表**。用 iNat2021 预训练 backbone（10k 物种）替换 ImageNet-59，重跑同一套评测；预期 top-5 里出现正确物种。
2. **D+2：小样本微调判据**。冻结 backbone 提特征 + 逻辑回归，20 种本地鸟 × 30 张，看 top-3 能否 >0.7；能则"客户端只跑特征、云端跑头"也可行。
3. **产品侧硬约束**：提示"把鸟放到画面中央并靠近/变焦"，用 bbox 短边 ≥64px 作为"可识别"门槛，低于门槛只提示"发现鸟"，不给物种。
4. **真机 spike**（与上面并行）：`onCameraFrame` 实测帧率/尺寸、`wx.createInferenceSession` 可用性、`WXWebAssembly` 跑 onnx 的可行性。
5. 若要提升小目标：先试 imgsz=960 + 目标区域裁切二次推理（只在"用户手指点选/长焦模式"下触发），比全局 1280 便宜。

## 10. 本次实验的局限（写进结论时要一起说）

- 召回是**相对参照**，参照本身会漏检（yolo11x@1280 也有 64–128px 的漏检），所以绝对值偏保守/偏乐观都可能。
- 只测了 2 段视频、各 300 帧（10 s），鸟种 2–3 个，**不能外推到"任意校园/公园场景"**。
- 退化变体是**合成**的（缩放/变暗/模糊/画枝条），不是真实远距/夜间素材。
- 物种分类只测了 ImageNet 词表，**没有测过真正的鸟类专用分类器**，所以"物种不可用"只针对当前选型。
