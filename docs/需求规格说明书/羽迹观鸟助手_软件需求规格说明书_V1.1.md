## 1. 简介

### 1.1 编写目的

本文档用于统一羽迹观鸟助手的产品范围、业务语义、外部接口、质量要求和验收方法，作为产品设计、前端开发、业务后端开发、模型服务开发、测试、部署和课程验收的共同依据。

本文档的直接读者包括项目组成员、需求评审人、测试人员和后续维护者。开发人员应能够由本文确定“做什么”和接口边界；测试人员应能够由需求编号编写可复现的验收用例；评审人应能够区分产品目标、已实现能力和尚未验证的假设。

### 1.2 产品范围

羽迹是一款面向城市观鸟新手和普通爱好者的微信小程序，围绕“探索—辨识—记录—整理—分享”形成闭环。用户可浏览附近公开鸟讯和观鸟地点，在现场打开相机获得实时鸟体框与候选鸟种，也可导入历史照片或录制鸟声；用户复核候选后，将原始证据、观察时间、位置和个人判断保存为私人观察，并自主决定是否加入收藏、发布到地图或论坛。

本项目的核心价值不是替用户自动宣判鸟种，而是提供可追溯的候选、明确的不确定状态和不丢失的观察证据。模型候选、用户确认与专家/社区复核必须分别保存和展示。

本需求基线包括以下系统组成：

- 微信小程序前端：地图、识别、记录、收藏、讨论与个人中心；
- 公网业务后端：微信登录、用户和观察数据、权限、媒体、地图与社区业务、对 GPU 服务的安全代理；
- GPU 视觉识别服务：鸟体检测、会话跟踪、鸟种候选、拒识、时空候选过滤和实时事件；
- 后续独立音频识别服务：BirdNET 推理、连续窗确认与负样本拒识；
- 业务数据库、对象存储、缓存与外部开放数据适配层。

### 1.3 范围外事项

本阶段不承诺：从零训练全球鸟种大模型；自动确认所有鸟种；把模型分数表述为正确率；根据轨迹编号推断鸟只数量；未经授权抓取国内观鸟社区；公开敏感鸟种精确坐标；在手机端处理完整 30 FPS 视频；生态健康诊断、种群估算或迁徙预测；将用户私人素材自动用于公开展示或模型训练。

### 1.4 术语与缩略语

| 术语 | 定义 |
|---|---|
| 观察（Observation） | 用户在某一时间、地点形成的一条观鸟事实记录，可包含照片、录音、备注和鉴定状态 |
| 观察时间 | 鸟实际被观察或素材被拍摄的时间，不等同于上传时间 |
| 候选（Candidate） | 模型通过工程门槛后给出的建议，仍需用户确认 |
| 待鉴定（Unknown） | 无可靠候选或用户尚不能确认的状态，不等同于系统错误 |
| 拒识 | 当相似度不足或候选过于接近时不强制给出鸟名 |
| Track ID | 单次实时会话内的短期画面轨迹编号，不是鸟的永久身份或数量 |
| ByteTrack | 将连续帧检测框关联为短期轨迹的多目标跟踪算法 |
| BioCLIP 2 | 视觉与生物分类文本进行相似度匹配的开放词表模型 |
| YOLO11n | 本项目用于检测 COCO `bird` 类的轻量目标检测模型 |
| BirdNET | 用于鸟声候选识别的预训练模型系列 |
| AviList | 本项目鸟类分类学主名录，当前目录版本为 v2026 |
| GBIF | 全球生物多样性信息机构；本项目用其经审核出现记录构建离线地点/月度候选集 |
| WGS84 / GCJ-02 | GPS/开放数据常用坐标系 / 中国境内高德地图展示坐标系 |
| P95 | 95% 请求不超过的延迟分位值 |
| RFC 3339 | 带时区的时间字符串格式，如 `2026-10-24T10:30:00+08:00` |

## 2. 综合描述

### 2.1 产品背景与目标

初学者常常不知道去哪里、何时去、如何分辨相似鸟种；已有经验的用户又面临照片、录音、地点和笔记分散、难以整理的问题。羽迹将开放地点数据、智能候选和个人记录串联起来，使一次观鸟活动留下可复核、可修改、可检索的长期档案。

产品目标如下：

1. 降低第一次发现、拍摄和记录鸟类的门槛；
2. 在实时界面中尽快发现鸟体，并仅在证据足够时提示候选鸟种；
3. 让照片、声音、观察时间、位置和用户判断形成同一条可追溯记录；
4. 识别失败、网络中断或权限被拒绝时仍允许保留素材和待鉴定记录；
5. 由用户控制私人保存、收藏、地图贡献和论坛发布；
6. 对位置隐私、敏感物种和第三方数据许可采取保守默认值。

### 2.2 产品视角与系统边界

系统采用“小程序 + 公网业务网关 + 独立 GPU 推理服务”的分层结构：

```text
微信小程序
  ├─ 地图、相机预览、录音、相册、记录表单
  ├─ 采集 captured_at / time_precision / latitude / longitude
  └─ 2～5 FPS 抽帧；本地预览保持流畅
          │ HTTPS / WSS
          ▼
公网业务后端（必须公网可达）
  ├─ 微信登录、用户/权限、限流与审计
  ├─ 观察记录、收藏、地图贡献、帖子与对象存储
  ├─ 外部数据聚合、缓存、脱敏与坐标转换
  └─ 持有 GPU 服务长期密钥；向小程序签发业务会话
          │ 内部 HTTPS / WSS，粘性会话路由
          ▼
GPU 视觉识别服务（当前仓库已实现）
  ├─ 图片校验 → YOLO11n 鸟体检测 → ByteTrack
  ├─ 最佳裁剪 → 时空候选集 → BioCLIP 2 排序/拒识
  └─ 最新帧背压、WebSocket 事件、指标和健康检查
          │
          ├─ AviList v2026 名录
          └─ 经审核的 GBIF 离线出现索引
```

小程序不得持有 GPU 服务长期 API Key，不得绕过业务后端直接建立生产会话。GPU 服务只负责短时推理，不负责用户、永久观察记录和公开内容。

### 2.3 用户类别

| 注册观鸟者 | 入门或普通爱好者 | 辨识、记录、收藏和分享自己的观察 | 管理本人私人数据和公开副本 |

### 2.5 运行环境与约束

- 客户端为微信小程序，具体最低基础库版本在前端工程建立时锁定并记录；
- 正式接口必须使用 HTTPS/WSS 和稳定域名；
- GPU 服务面向 NVIDIA CUDA 环境，当前云容器为 RTX 5090 8 GB 显存；单 GPU 默认一个模型进程；
- 公网 2 vCPU 服务器适合业务网关、数据库和静态接口，不承担 BioCLIP 2 高并发 GPU 推理；
- 云 GPU 可能按小时计费并在关机后不可访问，业务层必须有“识别暂不可用/稍后重试/保存待鉴定”的降级流程；
- 微信小程序摄像头、相册、麦克风和定位均受用户授权控制，拒绝单项权限不得阻断其他可用流程；
- GPS、eBird、iNaturalist、GBIF 统一以 WGS84 存储；仅在高德地图展示边界使用官方方式转换为 GCJ-02；
- 第三方 API 密钥只能保存在服务端；缓存、署名、敏感坐标和再分发必须遵守对应条款。

### 3.3 样本范围与统计边界

问卷共 22 题。第 1 题显示 31 份有效回答，多数统计题也以 31 份为基数；第 3 题为 30 份；第 2 题和第 5 题各只有 1 份有效回答，不能据此推断整体活动频率或“唯一首选功能”。第 13、21 题为开放题，导出文件没有提供回答文本，因此不能自行编写用户引语或主题结论。

多选题各项比例之和可以超过 100%；指定筛选后的图表未重新归一化。第 1 题“无观鸟经历”为 96.77%，但第 14～20、22 题中的经验状态并不一致，说明存在题目理解或跳题逻辑问题。因此，本轮结果用于发现需求信号和排序假设，不作为全部潜在用户的总体统计，也不用于计算市场规模、留存率或付费意愿。

### 3.4 关键调研结果

| 主题 | 结果 | 需求解释 |
|---|---:|---|
| 观鸟经历 | 无经历 96.77%，有经历 3.23% | 样本以入门者自报为主，优先降低地点选择、开始辨识和记录门槛 |
| 未参与原因 | 没有兴趣 46.67%；此前不了解 33.33%；不知道去哪/何时去、担心认不出均 30.00% | “缺少兴趣”和“缺少行动信息”须分开；工具主要服务已经有条件兴趣的人 |
| 期望功能 | 地图 77.42%；照片识鸟 58.06%；行前规划 41.94%；辨识学习 25.81% | P0 围绕地图、照片辨识、复核与记录形成闭环 |
| 输入方式 | 手机直接拍照 61.29%；相册 51.61%；声音 25.81%；实时提示 19.35% | 先保证拍照/相册，鸟声和实时相机分阶段验证 |
| 识别结果 | 少量候选并说明差异/不确定性 48.39%；单一最可能鸟名 41.94% | 首屏可突出第一候选，但必须保留候选比较、依据和待鉴定 |
| 弱网 | 先保存记录、联网后再识别 54.84%；还需离线资料 19.35% | 离线草稿和待同步状态为 P0，端侧完整模型不是 P0 前提 |
| 条件试用 | 比较愿意 58.06%，肯定愿意 9.68%，合计 67.74% | 可组织任务式原型试用，但不能当作真实使用率 |
| 停止使用因素 | 使用机会少 54.84%；步骤繁多 25.81%；识别不可靠 22.58%；付费 19.35% | 核心流程要短，减少重复录入，失败和不确定状态必须可信 |
| 分享偏好 | 照片指定对象 48.39%；记录指定对象 38.71% | 私人保存、指定分享和公开必须分离，不以公开作为保存前提 |
| 位置偏好 | 指定对象 29.03%；仅区域名 19.35%；每条决定 19.35%；较精确公开仅 6.45% | 位置默认保守，区分区域和精确坐标，逐条确认 |
| 现场痛点 | 看见鸟但无法确定 22.58%；地点/鸟讯分散及鸟讯依据不足均 12.90% | 识别候选、来源时间和地图信息应联合设计 |
| 照片整理 | 连拍整理痛点为 0%；缺少已完成整理耗时数据 | 不把批量照片整理列为首版核心，先向真实摄影用户补充调研 |

综合结果形成首版主流程：**查找地点 → 查看鸟讯时间、来源和到达条件 → 拍摄或选择照片 → 核对候选与关键区别 → 保存私人记录 → 自主选择分享范围。** 弱网时先保存素材和表单，联网后继续识别。

### 3.5 典型用户、场景与痛点

由于问卷不含可用的个体级交叉数据，以下角色是基于任务的典型用户，不是假装从 31 份回答中聚类得到的统计画像。

| 典型用户 | 主要特征与场景 | 核心目标 | 主要痛点 | 产品支持 |
|---|---|---|---|---|
| U1 城市入门探索者（主要用户） | 大学生或城市自然爱好者，尚无稳定观鸟经历，周末有短时户外需求 | 找到适合新手的地点，认出常见鸟并留下第一次记录 | 不知道去哪和何时去；担心认不出；不了解准备事项；使用机会少 | 地图与地点卡、简明行前提示、照片候选、待鉴定保存 |
| U2 偶尔拍摄与记录者（主要用户） | 已会随手拍照或录音，但没有固定记录工具 | 现场快速获得线索，回家后补全并回看记录 | 远距离照片模糊；相似鸟难分；照片、时间、位置和笔记分散；弱网 | 相机/相册、候选比较、自动带入真实时间位置、离线草稿和个人档案 |
| U3 经验鸟友或社团组织者（扩展用户） | 能复核常见鸟，关心来源质量、活动和多人交流 | 分享有来源的鸟讯，帮助新人，维护可信记录 | 公开位置风险；重复解释；机器结果被误当结论；团队记录与个人记录混淆 | 来源与时间标注、位置脱敏、复核历史、公开副本、活动与协作 P1/P2 |

| 用户旅程 | 痛点问题 | 需求响应 |
|---|---|---|
| 决定是否出门 | 信息分散，不知道附近是否适合、鸟讯是否过时 | 附近地图、地点详情、观察时间和来源、交通与访问条件 |
| 现场发现鸟 | 鸟小、移动快、拍不清，不知道观察哪些特征 | 实时鸟框或拍照入口、拍摄质量提示、关键区别和补充观察建议 |

### 3.6 用户故事优先级与难度评估方法

优先级综合问卷信号、是否构成“地图—辨识—记录”主流程、失败时的数据安全和课程版本依赖关系确定：P0 为闭环和基础保障，P1 为有需求信号但依赖较多的增强，P2 为证据不足或成本较高的探索。技术难度按前端设备能力、业务状态复杂度、外部数据/许可、模型不确定性和跨服务联调综合评为低、中、高。

实时相机的问卷功能期望为 12.90%、输入偏好为 19.35%，弱于地图和照片识别。团队仍将其提升为课程项目 P0，是因为即时识别已经被确定为项目差异化演示目标，且视觉后端预研已显著降低技术未知；这属于项目范围决策，不伪装成问卷首选结论。产品必须同时保留需求证据更强的静态拍照/相册入口和低成本降级路径。

### 5.2 鉴定状态模型

观察的鉴定状态必须使用显式状态机：

```text
待鉴定 unknown
   ├─ 用户选择/手工录入 ──> 用户已标注 user_identified
   ├─ 社区提出建议 ──────> 仍为 unknown + review_suggestions
   └─ 授权复核者确认 ────> 已复核 reviewed

user_identified ── 用户更正 ──> user_identified（新增 revision）
user_identified ── 复核通过/纠正 ──> reviewed（保留原历史）
```

模型状态 `candidate` 只属于 ModelEvidence，不得直接映射成 `reviewed`。用户点击候选后才形成 `user_identified`；系统应保留“用户选择来自哪个候选”的关系。

### 5.3 时间规则

系统必须区分：

- `observed_at` / `captured_at`：观察或拍摄时间；
- `uploaded_at`：文件到达服务器时间；
- `created_at`：业务记录创建时间；
- `time_precision`：`exact`、`date`、`month` 或 `unknown`；
- `time_source`：相机当前时间、EXIF、文件名、用户输入或未知。

实时帧使用当前设备时间且必须带时区。历史照片优先使用 EXIF；若只有日期或月份，应降低精度；若真实月份未知，不得使用文件修改时间驱动季节筛选。服务端保存 UTC 时间用于计算，同时保留原时区/精度供展示和审计。

### 5.4 位置规则

- 经度和纬度必须成对出现，范围分别为 `[-180,180]` 和 `[-90,90]`；
- 私人观察允许没有位置；定位拒绝不得阻止保存；
- 推理服务只在内存中使用位置选择候选，当前不持久化帧或坐标；
- 业务后端若持久化精确位置，必须与公开位置分别存储；
- 敏感物种、巢址、夜栖地和私人住址不得原样公开；
- EXIF、照片背景、时间、相邻记录也可能泄露位置，公开导出时应清除非必要元数据；
- 匿名和位置保护是两个独立开关。

### 5.5 分类名录与出现数据

分类主键应使用稳定 `species_id`，显示名称按中文、英文、学名回退。当前视觉服务加载 AviList v2026：总计 11,172 条、启用 10,970 条；灭绝或停用条目保留于目录但不进入实时候选。

经纬度和月份提供严格优先的当地候选：当地 Top-1 达到最低相似度时为 `local_seasonal`，并在当地列表内完成接受或歧义拒识；只有当地 Top-1 过低、记录缺失、不可用或不足时为 `global`。GBIF 出现次数仅用于审计和解释，不参与相似度加分；响应必须返回实际范围与回退原因。

### 5.6 数据保留与删除

| 数据 | 默认保留 | 删除/过期规则 |
|---|---|---|
| GPU 上传帧 | 不持久化 | 请求结束、队列替换或会话清理后释放 |
| GPU 会话 | 短时内存 | 显式关闭或空闲超时后清理 |
| 私人观察和原始素材 | 用户持有期间 | 用户删除后进入可恢复期；到期物理清理，具体期限由隐私政策确定 |
| 公开副本 | 发布期间 | 撤回后从公开查询移除；审计只保留最小必要元数据 |
| 模型评测集 | 单独授权 | 不因保存观察自动进入训练/评测集 |
| 运行日志 | 运维最小期限 | 到期滚动删除；不得包含密钥和媒体内容 |

## 6. 总体架构、技术选型与外部接口

### 6.1 总体架构

系统采用前后端分离、业务与推理解耦的四层架构。微信小程序只持有用户级短期凭证；公网业务后端统一处理微信身份、对象权限、数据持久化、第三方 API 和 GPU 服务代理；GPU 视觉服务只处理短时推理；数据层分别保存结构化业务数据、媒体对象和缓存。该划分使无 GPU 的公网服务器承担稳定业务入口，按量云 GPU 可以独立开关、扩容和回滚。

```text
微信小程序（原生 TypeScript）
  ├─ 地图 / 相机 / 相册 / 麦克风 / 本地草稿
  └─ HTTPS + WSS，仅访问业务域名
               │
               ▼
公网业务后端（FastAPI）
  ├─ 微信登录、用户和对象级权限
  ├─ 观察 / 收藏 / 地图贡献 / 讨论
  ├─ 上传凭证、限流、审计、第三方数据适配
  └─ 识别会话代理与 GPU 不可用降级
       │                 │
       ▼                 ▼
PostgreSQL / Redis / 对象存储    云 GPU 视觉服务
                               YOLO11n → ByteTrack
                               → 时空候选 → BioCLIP 2 / 拒识
                               │
                               └─ AviList + 离线 GBIF 索引
```

同一实时会话的 HTTP 帧与 WebSocket 必须粘性路由到同一 GPU Worker。业务后端不把微信令牌转发给 GPU，GPU 长期密钥也不下发至小程序。

### 6.2 技术选型

| 层次 | 最终选型 | 选择理由 | 当前状态 |
|---|---|---|---|
| 小程序前端 | 微信小程序原生框架 + TypeScript | 相机、定位、地图、WebSocket 和授权能力路径最短；四人课程团队无需额外跨端抽象 | 待建立正式工程；已有 HTML 交互原型 |
| UI 与状态 | 原生组件、页面级状态、统一请求/错误封装 | 减少依赖和包体；先保证核心流程与异常状态，复杂全局状态再按需引入 | 设计完成 |
| 公网业务后端 | Python 3.12 + FastAPI + Pydantic 2 | 与现有视觉服务技术栈一致；异步 HTTP/WebSocket 与 OpenAPI 支持成熟 | 待实现 |
| 数据访问与迁移 | SQLAlchemy 2 + Alembic | 显式事务、模型关系和可审计迁移，适合观察/公开副本等关系数据 | 待实现 |
| 业务数据库 | PostgreSQL 16 | 支持事务、JSONB、全文/地理扩展和可靠约束；比把核心数据放在缓存中稳健 | 待部署 |
| 缓存与限流 | Redis 7 | 会话、幂等、限流、短期热点数据和任务状态；不作为唯一持久存储 | P1，待部署 |
| 媒体存储 | S3 兼容对象存储；本地开发用 MinIO | 原图不适合进入数据库；可使用预签名上传、生命周期和校验和 | 待实现 |
| 反向代理 | Nginx/Caddy + HTTPS/WSS | 提供稳定域名、TLS、上传限制、WebSocket 转发和流量切换 | 待部署 |
| 视觉 API | FastAPI + Uvicorn，单 GPU 单进程 | 已实现异步会话、鉴权、背压、指标和健康检查 | 已实现 |
| 鸟体检测 | YOLO11n（COCO bird） | 轻量、预训练、检测速度适合抽帧；只负责“哪里有鸟” | 已实现 |
| 跟踪 | ByteTrack，会话级状态 | 利用高低置信框维持短期轨迹，避免每帧名称抖动 | 已实现 |
| 物种候选 | BioCLIP 2 + AviList v2026 | 开放词表覆盖全球名录，优于旧 59 类 ImageNet 词表 | 已实现，待实拍校准 |
| 时空候选 | WGS84 经纬度 + 拍摄月份 + 持久化 GBIF 区域缓存 | 提供可审计的当地优先候选；不以地区奖励修改模型分数，不硬排除未记录物种 | 任意坐标按需缓存已实现 |
| 鸟声 | BirdNET 独立服务 | 预训练覆盖广；3 秒窗与连续确认已预研，不与视觉进程强耦合 | P1，仅预研 |
| 地图 | 微信 `map` 组件 + 高德 Web 服务；内部保存 WGS84 | 国内展示与小程序集成方便；仅展示阶段转换 GCJ-02 | 待接入 |
| 外部鸟讯 | AviList 主表；eBird/iNaturalist 近期补充；GBIF 历史聚合 | 分类、近期记录和历史出现各司其职，服务端处理许可与敏感坐标 | 调研完成，待接入 |
| 测试与 CI | Pytest、Ruff、GitHub Actions、固定实拍评测集 | 当前后端已有 199 项测试与覆盖率门槛；模型质量另用版本化数据集 | 后端已接入 |
| 部署 | 公网 CPU 业务服务器 + 按量云 GPU 容器，模型离线加载 | 控制成本；GPU 可独立启停；公网入口不依赖研究组内网 | GPU 侧已可部署 |

### 6.3 关键选型决策

1. 不把完整视频上传到服务器：本地保持预览，仅抽取 2～5 FPS 最新帧，减少带宽和旧帧积压。
2. 不让小程序直连 GPU：业务网关负责用户权限、限流和密钥隔离，GPU 服务可按量启停。
3. 不采用端到端“一个模型直接给鸟名”：检测、跟踪、候选过滤、分类和拒识分层，便于解释和替换。
4. 不把 Redis 或文件目录当业务数据库：观察、公开副本和修订历史需要事务与约束。
5. 不把用户保存等同于训练授权：私人记录、公开分享、参考复用和模型训练分别授权。
6. 不依赖运行时访问 Hugging Face：模型和名录在部署前下载、校验并置于持久盘，生产启动使用离线模式。

| 摄像头 | 相机权限 | 本地预览、抽样帧、设备时间 | 转相册或文字记录 |
| 相册 | 相册/隐私授权 | 图片、可用 EXIF 时间与 GPS | 允许用户手动填写或未知 |
| 麦克风 | 麦克风权限 | 音频片段、录制时间 | 转照片/文字记录 |

### 6.5 业务后端接口原则

业务接口统一使用 `/api/v1`，返回 JSON，时间使用 RFC 3339，写操作支持幂等键，分页接口返回稳定游标或 `offset/limit`。错误体至少包含 `code`、可安全展示的 `message` 和 `request_id`。小程序只访问业务域名；业务网关负责微信身份换取、用户级鉴权、限流、对象权限和调用 GPU 服务。

建议业务 API 分组：

| 分组 | 示例资源 |
|---|---|
| `/auth`、`/users` | 微信登录、当前用户、资料与授权 |
| `/observations` | 观察 CRUD、证据、修订、待同步 |
| `/media` | 上传凭证、分片上传、校验和、缩略图 |
| `/places`、`/map-contributions` | 地点、公开观察、选点与撤回 |
| `/collections` | 个人收藏、图鉴和书签 |
| `/posts`、`/replies` | 讨论、回复、举报 |
| `/recognition/vision` | 对 GPU 会话、帧和事件的用户级代理 |
| `/recognition/audio` | 鸟声任务与结果（P1） |

### 6.6 视觉会话 API 合同

#### 6.6.1 创建会话

`POST /api/v1/vision/sessions`

```json
{
  "client_session_id": "wx-activity-20261024-001",
  "observation_mode": "live",
  "latitude": 31.8206,
  "longitude": 117.2272,
  "region_code": "CN"
}
```

| 字段 | 必填 | 约束 | 前端来源 |
|---|---:|---|---|
| `client_session_id` | 否 | 调用链关联 ID | 前端/业务后端生成 |
| `observation_mode` | 是 | `live` 或 `historical` | 实时相机为 live，相册为 historical |
| `latitude` | 否 | `[-90,90]`，与经度成对 | 定位、EXIF 或用户选点 |
| `longitude` | 否 | `[-180,180]`，与纬度成对 | 定位、EXIF 或用户选点 |
| `region_code` | 否 | ISO 3166-1 两位大写代码 | 服务端地理判断或用户区域 |

成功返回 `201`，包含服务器 `session_id`、空闲有效期、建议帧间隔和 WebSocket 路径。前端必须使用服务器返回的 `session_id`，不得把客户端 ID 当作鉴权依据。

#### 6.6.2 上传照片/实时帧

`POST /api/v1/vision/sessions/{session_id}/frames`，`multipart/form-data`

| 字段 | 必填 | 类型/约束 | 说明 |
|---|---:|---|---|
| `frame` | 是 | JPEG/PNG/WebP；默认 ≤6 MiB、≤8,294,400 像素 | 照片或抽样帧 |
| `frame_id` | 是 | 1～128 位安全字符，会话内唯一 | 幂等和结果关联 |
| `captured_at` | live 建议；historical 必须 | RFC 3339，必须带时区 | **前端传入真实拍摄/采集时间** |
| `capture_time_precision` | 否 | `exact/date/month/unknown` | 不知道真实月份必须传 unknown |
| `latitude` | 否 | 与经度成对 | **前端可按每张照片覆盖位置** |
| `longitude` | 否 | 与纬度成对 | **前端可按每张照片覆盖位置** |

正式前端传参算法必须满足：

```text
实时相机：
  captured_at = 当前帧采集时刻（带本地时区）
  capture_time_precision = exact
  coordinates = 已授权且可用的当前定位；否则不传

历史照片：
  captured_at = EXIF DateTimeOriginal > 用户输入 > 明确的已知日期/月
  capture_time_precision = 与来源真实精度一致
  coordinates = EXIF GPS > 用户确认选点 > 不传
  若真实时间未知：标记 unknown，不使用下载时间/mtime伪装
```

服务接收并排队后返回 `202`；推理结果通过 WebSocket 异步发送。重复 `frame_id` 返回 `409`，过载返回 `429/503` 并带 `Retry-After`。

#### 6.6.3 WebSocket 结果

`WSS /api/v1/vision/sessions/{session_id}/events`

主要事件：

| 事件 | 用途 |
|---|---|
| `vision.session.started` | 确认上下文、建议频率和目录版本 |
| `vision.heartbeat` | 连接存活；默认 15 秒 |
| `vision.frame.result` | 鸟框、轨迹、候选、决策、上下文和耗时 |
| `vision.frame.dropped` | 旧帧被新帧替换或排队过期 |
| `vision.frame.error` | 单帧失败；会话不一定关闭 |

前端至少消费以下结果字段：`frame_id`、`captured_at`、`observation_context`、`tracks[].bbox`、`tracks[].visibility`、`tracks[].species.state`、`candidates`、`decision.candidate_scope`、`decision.fallback_reason` 和 `timing.total_ms`。

### 6.7 视觉服务运维 API

| 方法与路径 | 鉴权 | 作用 |
|---|---|---|
| `GET /healthz` | 无 | 仅证明进程存活 |
| `GET /readyz` | 无 | 证明检测器、分类器和运行时可接流量 |
| `GET /api/v1/models` | 服务密钥 | 模型、后端、设备、阈值和版本 |

## 7. 非功能需求

### 7.1 性能与容量

| 编号 | 指标 | 目标/约束 | 验收环境 |
|---|---|---|---|
| NFR-PERF-001 | 本地相机预览 | 视觉上连续，目标 ≥24 FPS；上传抽样不阻塞 UI | 主流真机 |
| NFR-PERF-002 | 抽帧频率 | 默认 2～5 FPS，服从服务建议间隔 | 真机 + 公网 |
| NFR-PERF-003 | 首个鸟框 | P95 ≤1.0 秒（从帧上传完成到结果事件） | 固定网络与云 GPU |
| NFR-PERF-004 | 候选更新 | 可识别鸟体稳定后 P95 ≤3.0 秒 | 固定实拍视频集 |
| NFR-PERF-005 | 单帧推理 | 记录 queue/decode/detection/species/total 分段延迟，不以单次最佳值验收 | RTX 5090 部署 |
| NFR-PERF-006 | 会话背压 | 每会话队列为 1；旧帧可丢，最新帧不可长期饿死 | 人工注入慢推理 |
| NFR-PERF-007 | 单帧限制 | 默认 ≤6 MiB、≤4K 像素 | API 边界测试 |
| NFR-PERF-008 | 并发 | 发布前在实际显存上确定单实例安全会话数；不得以开发机估算冒充结果 | 压测报告 |

若准确率与实时性冲突，默认优先保证预览流畅、最新帧和保守拒识；不为追求每帧处理而积压过时画面。

### 7.2 可用性与容错

- 核心私人记录流程目标月可用性不低于 99.5%；第三方数据和 GPU 识别不可用不得阻止草稿和待鉴定保存；
- 客户端网络重试采用指数退避并设置上限；写操作使用幂等键；
- WebSocket 中断后可以重连，断线期间事件不保证补发，界面必须明确“正在重连/结果可能过期”；
- 生产就绪探针失败时网关不再创建新推理会话；
- 对象存储上传、业务记录写入和公开发布必须分阶段报告，不能把部分成功显示为全部成功；
- 云 GPU 开关机和模型冷启动状态应在运维面板可见。

### 7.3 安全

| 编号 | 需求 |
|---|---|
| NFR-SEC-001 | 所有生产通信使用 TLS；禁止明文 HTTP/WS 和跳过证书校验。 |
| NFR-SEC-002 | 小程序令牌、业务服务密钥和 GPU 服务密钥分层，密钥可轮换且不进入仓库。 |
| NFR-SEC-003 | 所有对象访问实施服务端所有权校验；禁止只依赖前端隐藏按钮。 |
| NFR-SEC-004 | 上传内容同时校验长度、MIME、魔数、解码尺寸和资源预算，防止压缩炸弹与内存耗尽。 |
| NFR-SEC-005 | 用户输入、文件名和第三方文本在展示前转义；数据库使用参数化查询。 |
| NFR-SEC-006 | 登录、上传、识别、发帖和管理接口分别限流；异常行为产生审计与告警。 |
| NFR-SEC-007 | 错误响应不泄露堆栈、本地路径、模型凭证、其他用户会话或数据库细节。 |

### 7.4 隐私与合规

- 数据最小化：不为推理强制要求位置；只收集实现用户选择功能所需字段；
- 用途分离：私人保存、公开分享、参考样本和模型训练分别授权；
- 可见性默认私人；公开前以最终将展示的快照再次确认；
- 精确位置和原图 EXIF 按敏感数据处理，传输和存储加密；
- 对敏感鸟种、巢址和夜栖地执行隐藏、模糊或延迟发布策略；
- 第三方观察数据保留来源、许可证和原平台隐私状态，不尝试逆向恢复模糊坐标；
- 隐私政策必须说明数据类型、用途、保留期、共享对象、撤回方式和联系渠道。

### 7.5 易用性与无障碍

- 相机页核心操作单手可达，处理中、重连、无候选、服务失败、保存失败状态清晰区分；
- 不能仅用红/绿表达鉴定状态；文字和图标同时提示；
- 关键文本满足可读对比度，按钮具备足够点击区域；
- 中文为默认语言，鸟名缺失时按英文名、学名回退；
- 用户退出识别页前若存在未保存素材，必须确认保留或丢弃；
- 专业术语提供简短解释，如“候选不是确认”“轨迹编号不是数量”。

### 7.6 可维护性与可观测性

- API 使用版本前缀；在 v1 中新增可选字段可兼容，删除字段或改变状态/坐标语义须升级版本；
- 前端必须忽略未知 JSON 字段和未知事件类型；
- Python 依赖分基础、开发、CPU 测试和 GPU 层锁定；Torch/CUDA 与云镜像作为底层兼容边界单独管理；
- 代码提交通过格式检查、静态检查、单元测试和覆盖率门槛；
- 日志使用 `request_id`、会话 ID 和帧 ID 关联，不记录媒体；
- 指标至少包含 HTTP 延迟、结果状态、丢帧数、推理分段延迟、活动会话、GPU 错误和就绪状态；
- 模型或名录升级前后必须运行同一固定集并保存可比较报告。

### 7.7 模型质量

模型质量必须以版本化实拍集评估，不使用“看起来正确”的零散样例代替：

| 集合 | 最低内容 | 指标 |
|---|---|---|
| 正样本 | 合肥常见鸟、相似种、远距离、小目标、遮挡、逆光、手机变焦 | 鸟体召回、Top-1/Top-5、候选接受率、分类延迟 |
| 困难正样本 | 雌雄/幼鸟/季节羽、鹰鹃等易混淆鸟 | 混淆矩阵、拒识与人工复核率 |
| 负样本 | 无鸟风景、玩具、雕塑、飞机、模糊纹理 | 误检率、错误候选接受率 |
| 开集样本 | 目录外或地点索引外鸟种 | 拒识率、回退路径正确性 |
| 连续视频 | 多鸟、交叉、短暂遮挡、镜头运动 | ID 稳定、错误换名、首框和候选延迟 |

默认阈值 `0.20/0.01` 仅是工程起点，不是经校准的通用结论。发布门槛和目标数值必须由固定数据集报告给出并经项目组签字。

## 8. 验收与需求追踪

### 8.1 核心端到端验收场景

| 编号 | 场景 | 前置条件 | 通过标准 |
|---|---|---|---|
| AT-01 | 实时相机识别 | 相机、网络、GPU 可用；定位允许 | 进入即预览；抓包含 live、准确时间和位置；鸟框/候选异步更新；用户确认后才能保存鸟名 |
| AT-02 | 定位被拒绝 | 相机可用，定位拒绝 | 不上传伪造坐标；仍可识别；界面提示候选范围降级；可保存无位置记录 |
| AT-03 | 历史照片含 EXIF | 照片有原始时间/GPS | 前端展示并传 historical、EXIF 时间/精度和坐标；响应回显来源；用户可修改 |
| AT-04 | 历史照片无时间 | 照片无可靠 EXIF | 不用 mtime 冒充；用户可选未知；服务采用全年候选或回退；记录显示时间未知 |
| AT-05 | 低质量鸟体 | 鸟短边小于门槛或严重模糊 | 只提示发现鸟/改善拍摄，不给确定鸟名 |
| AT-06 | 无可靠候选 | 相似度或间隔不足 | 状态为 unknown；可保存待鉴定；Top-K 不自动写入记录 |
| AT-07 | GPU 不可用 | `/readyz` 为 503 | 前端明确降级；素材和备注不丢失；允许待鉴定保存或稍后重试 |
| AT-08 | 网络抖动和积压 | 注入延迟、断开 WebSocket | 旧帧被替换；重连后显示最新结果；不形成重复观察 |
| AT-09 | 隐私发布 | 私人观察含精确位置/EXIF | 发布前预览；敏感位置处理；撤回公开副本不删除私人原件 |
| AT-10 | 双会话隔离 | 两个凭证并行识别 | 不能读取对方会话；轨迹、帧 ID 和结果不串线 |

### 8.2 前端时间与位置专项验收

该专项用于回答“前端传照片时是否真的把时间和位置传入”，必须以运行证据判定，不以接口文档代替：

1. 在微信开发者工具和至少一台真机中分别运行相机与相册流程；
2. 通过业务网关结构化日志或受控抓包，确认创建会话含 `observation_mode`，允许定位时含经纬度；
3. 确认每次帧请求含唯一 `frame_id`、带时区 `captured_at` 和正确 `capture_time_precision`；
4. 使用含 EXIF、无 EXIF、仅日期、错误未来时间和定位拒绝五组样例；
5. 核对服务端 `observation_context.observed_at/time_source/time_precision/coordinate_source`；
6. 核对位置与月份变化会改变 `candidate_scope/observation_month`，但不会给模型分数添加地区奖励；
7. 将脱敏后的请求/响应、真机截图和测试用例结果归档为验收附件。

在以上证据齐全前，该项状态只能标记为“后端接口已支持，正式前端未验收”。

### 8.5 提交与发布门槛

## 9. 风险、限制与发布策略

### 9.1 主要风险

| 风险 | 影响 | 概率 | 应对 |
|---|---|---:|---|
| 日常远距离照片主体过小 | 能发现鸟但无法可靠分种 | 高 | 质量门槛、变焦引导、最佳帧、待鉴定 |
| BioCLIP 开放词表相似种混淆 | 错误候选被用户误信 | 高 | 时空候选、双门槛拒识、候选措辞、实拍校准 |
| 地点索引不完整 | 真实罕见鸟被过滤 | 中 | 返回范围/回退原因、允许手工更正、定期更新数据 |
| 云 GPU 费用与停机 | 实时服务间歇不可用 | 中 | 按需启停、业务降级、保存待鉴定、演示前预热 |
| 小程序网络与 WebSocket 限制 | 结果延迟、断线 | 中 | 2～5 FPS、队列 1、心跳、退避重连、最新状态语义 |
| 无大量实拍数据 | 无法证明泛化效果 | 高 | 小规模分层固定集、公开许可样本、持续错误回收但不默认训练 |
| 外部 API 限流或许可变化 | 地图和鸟讯不可用 | 中 | 服务端适配器、缓存、来源状态、可替换提供方 |
| 精确位置泄露 | 用户隐私或鸟类保护风险 | 高 | 私人默认、公开预览、敏感策略、EXIF 清理与审计 |
| 模型/依赖与 CUDA 不兼容 | 部署失败 | 中 | 底层镜像冻结、分层依赖锁、wheelhouse、启动自检、回滚 |

### 9.2 分阶段发布

| 阶段 | 内容 | 退出条件 |
|---|---|---|
| 内部联调 | Mock/固定图、业务接口、前端状态机 | 契约测试通过，无需外部用户 |
| GPU 技术验收 | 真实模型、固定图片/视频集、断网启动 | 性能、拒识、依赖和离线加载报告通过 |
| 小范围试用 | 合肥/校园周边、受邀用户、默认私人 | 核心流程可用，隐私与失败反馈无阻断问题 |
| 课程演示 | 锁定版本、预热 GPU、准备降级素材 | 发布清单、回滚和演示脚本完整 |
| 扩大试点 | 更多地点与用户 | 数据许可、运维成本和模型指标经重新评审 |

### 9.3 尚待决策事项

### 10.3 每轮完成定义

一个故事只有同时满足以下条件才进入 Done：

1. 用户故事与验收条件没有未记录的语义变化；
2. 正常、权限拒绝、空数据、网络失败和服务失败路径均有处理；
3. 前后端契约测试或 Mock 已通过，真实接口字段与文档一致；
4. 代码通过格式检查、静态检查、单元/集成测试和非作者评审；
5. 影响隐私、公开范围、模型分数或位置的文案已经复核；
6. 页面有真机或目标尺寸证据，后端有日志/指标，模型有固定样例结果；
7. Issue 附交付链接、测试证据和已知限制，相关文档同步更新。

解释：`score` 是最终采用的当地或全球候选集合中的相对排序分数，`similarity` 是图像与文本提示的原始相似度，`local_occurrence_count` 是出现数据审计信息；三者都不是“识别正确率”。

## 附录 B：视觉 API 主要错误码

| HTTP | 错误码 | 客户端处理 |
|---:|---|---|
| 401 | `AUTH_REQUIRED` / `AUTH_INVALID` | 刷新业务会话或重新登录，不循环重试无效密钥 |
| 404 | `SESSION_NOT_FOUND` | 清理本地会话并重新创建，不提示他人会话存在 |
| 408 | `UPLOAD_TIMEOUT` | 降低图片大小并有限重试 |
| 409 | `FRAME_ID_DUPLICATE` | 不重发同一 ID；查询已有状态或生成新帧 ID |
| 409 | `SESSION_FRAME_CAPACITY_EXCEEDED` | 关闭旧会话并创建新会话 |
| 413 | `IMAGE_TOO_LARGE` / `IMAGE_DIMENSIONS_INVALID` | 客户端压缩/缩放，保留原图用于记录 |
| 415 | `UNSUPPORTED_IMAGE_TYPE` | 转换为 JPEG/PNG/WebP |
| 422 | `IMAGE_DECODE_FAILED` | 提示损坏或伪造格式，允许更换 |
| 422 | `CAPTURED_AT_TIMEZONE_REQUIRED` | 修复为带时区 RFC 3339 |
| 422 | `CAPTURED_AT_REQUIRED` | 历史图片补充真实时间或标记未知 |
| 422 | `CAPTURED_AT_CLOCK_SKEW` | 校准设备时间；历史会话不得传未来时间 |
| 422 | `COORDINATES_INCOMPLETE` | 成对传经纬度或全部省略 |
| 429 | `FRAME_RATE_EXCEEDED` / `FRAME_UPLOAD_IN_PROGRESS` | 遵循 `Retry-After` 并降低抽帧率 |
| 503 | `SESSION_CAPACITY_EXCEEDED` / `DECODE_CAPACITY_EXCEEDED` | 保存待鉴定、退避重试或使用降级服务 |

## 附录 D：结论

本需求基线将羽迹定义为“以真实观察证据为中心的观鸟助手”。问卷对地图、照片辨识、弱网先保存和保守位置分享给出了明确信号；对实时识别、批量整理和长期留存的证据较弱。因此，V1.1 把调研结论、样本局限、三类典型用户、故事地图、20 张故事卡与逐故事原型追踪纳入同一条证据链，并明确区分“问卷结论”与“课程项目范围决策”。

系统采用微信小程序、公网业务后端、业务数据层与独立 GPU 推理服务的分层架构。实时识别采用本地预览和 2～5 FPS 抽帧；时间与位置由前端在授权和真实性约束下传入，后端用其选择地点/月度候选集，但不以地区奖励篡改模型分数。系统允许候选、待鉴定、用户确认和复核并存，并在 GPU、网络、权限或模型失败时优先保证素材和观察记录不丢失。

截至 2026 年 10 月 24 日，仓库已经提供视觉服务技术基础和详细 API，正式微信小程序与业务数据层仍是后续开发任务。第 10 章将这一差异分解到两名前端、两名后端的周迭代、交付物和验收门槛中。项目组应以需求编号、故事卡和验收矩阵推进实现，任何范围、语义或接口变化均应记录修订版本。
