# 微信小程序平台约束核查表（视觉/音频落地前必须过）

> 状态说明：**本轮全部结论来自 PC（Python + CPU）**，以下每条都标了"是否已在本项目验证"。
> 未验证项必须在真机上跑一遍，否则"端侧可行"的结论不成立。

## A. 相机取帧

| # | 事项 | 结论/预期 | 验证方法 | 判定标准 | 状态 |
|---|---|---|---|---|---|
| A1 | `<camera>` + `CameraContext.onCameraFrame` 是否可用 | 官方标注**仅真机**，模拟器无回调；基础库 2.7.0+ | 真机跑最小 demo，统计 30 s 内回调次数 | 有回调且 `width/height` 正确 | ⬜ 未验证 |
| A2 | 回调帧格式与解码成本 | ArrayBuffer，格式随平台/基础库不同（RGBA / NV21 等），**必须实测**；转 RGB + resize 的成本不能忽略 | 打印 `frame` 字段，测 `new Uint8ClampedArray` → canvas/离屏绘制耗时 | 单帧格式转换 ≤10 ms | ⬜ 未验证 |
| A3 | 实际可达帧率 | 与设备强相关，预期 15–30 FPS | 统计 30 s 回调帧率 p50/p95 | ≥15 FPS 才谈得上"实时提示" | ⬜ 未验证 |
| A4 | 可选分辨率 | `camera` 的 `resolution` 支持 low/medium/high；**注意高分辨率不等于高帧率** | 分别测 3 档的 帧尺寸×帧率 | 至少一档能给出 ≥720p 且 ≥15 FPS | ⬜ 未验证 |
| A5 | 回调与 JS 主线程争用 | 推理是同步长任务会阻塞渲染 | 推理期间测 UI 掉帧 | 掉帧可接受或需 Worker/WASM 隔离 | ⬜ 未验证 |

**对本项目的影响**：PC 上 640 输入 17.6 ms。手机端先按 **2–5×** 估算（35–90 ms），
即"能实时画框，但每帧剩余预算不多"。若 A3 <15 FPS，产品形态应改为"点按拍摄 → 冻结帧分析"，而不是连续 AR 框。

## B. 端侧推理

| # | 事项 | 结论/预期 | 验证方法 | 判定标准 | 状态 |
|---|---|---|---|---|---|
| B1 | `wx.createInferenceSession` 能否加载 YOLO | 该接口面向微信自有推理引擎，模型需用官方工具转换，**算子/结构白名单有限**，通用 YOLO 导出能否通过为未知 | 用官方工具转 yolo11n，真机 `createInferenceSession` + `run` | 能加载并输出张量 | ⬜ 未验证（**最高风险项**） |
| B2 | `WXWebAssembly` 跑 onnxruntime-web | 可行路径之一，但内存上限、SIMD/多线程支持受限 | 加载 ort-wasm + yolo11n.onnx，测单帧耗时 | 单帧 ≤50 ms 且不 OOM | ⬜ 未验证 |
| B3 | 模型分发 | 不能打进主包（单包 2 MB / 总 20 MB）；需 CDN 下载 + `FileSystemManager` 缓存 | 首次/二次启动耗时 | 冷启动额外等待可接受（可做"首次使用时后台下载"） | ⬜ 未验证 |
| B4 | 手机端真实延迟 | 未知；PC 640 输入为 17.6 ms | 同一段视频在手机上跑（不走相机） | p95 ≤ 100 ms 视为可用 | ⬜ 未验证 |

**决策规则**：B1、B2 只要有一条打通且 B4 达标 → 端侧做"检测+跟踪"；否则**检测也走服务端**（抽帧上传，2–4 FPS 足够做提示）。

## C. 音频（为第二目标预留）

| # | 事项 | 结论/预期 | 验证方法 | 判定标准 | 状态 |
|---|---|---|---|---|---|
| C1 | 录音采样率 | `RecorderManager.start({sampleRate})` 支持范围依平台，48 kHz 不保证 | 真机分别录 44.1k/48k | 能拿到 48 kHz | ⬜ 未验证 |
| C2 | 能否拿到 PCM | `onFrameRecorded` 返回的是**编码帧**（mp3/aac），不是裸 PCM；需要端内解码 | 录音 + 解码测通 | 能还原 48 kHz 单声道 float | ⬜ 未验证 |
| C3 | 上传体积/延迟 | 3 s 单声道 16-bit 48 kHz ≈ 288 KB 裸 PCM；压成 opus/aac 约 20–40 KB | 实测 4G 上传 | ≤1 s 上传 | ⬜ 未验证 |

**已确认（本轮实测）**：BirdNET v2.4 输入是 **48 kHz / 144000 样本（3 s）的裸波形**，且**不支持动态窗长**；模型 FP32 就有 **49.3 MB**。
这意味着端侧要同时解决「拿到 48 kHz PCM」+「加载 49 MB 模型」+「算力」三件事，任一条不通就只能走服务端 —— 所以音频首版按服务端设计，端侧只做 VAD 触发。

**倾向性结论（待验证）**：音频首版**服务端推理**，端侧只做 VAD 触发，避免 C1/C2 卡死整条链路。

## D. 已确认的通用约束（本轮实测/文档确认）

1. **中文路径**：本机 `cv2.VideoCapture` 在 `d:\作业\软工\...` 下静默失败 —— 小程序侧无关，但**所有实验脚本必须走 ASCII 路径**（已在 `common.py` 处理）。
2. **CPU 是可用基线**：yolo11n@640 在笔记本 CPU 上 24 ms 端到端，说明"实时"不是靠 GPU 撑出来的；但 yolo11x 这类大模型在 CPU 上（841 ms）完全不可用，别把它当端侧候选。
3. **物种分类是第二段成本**：ResNet50 让 p95 从 27 ms → 57 ms。端侧要选 MobileNet/EfficientNet 级别，或把分类放服务端。
4. **不要把带标注的视频当输入**（`birds-track-compressed.mp4` 画面里已烧进框），否则指标虚高。
